# Part A 判断力

状态：A1、A2 已完成，包含源码依据、验证方案与 A2 已执行的测试记录。

## A1 当前时间与 system prompt

用户真正需要的是：不必反复提醒日期，AI 就能以正确的“现在”理解今天、这周等相对时间。若问的是这周发生的事情，还需要取得这一时间范围内的事实。下面分别回答三个问题。

### 1. 是否同意同事的方案？问题在哪里？

**同意由产品自动提供当前时间，但不同意把每次请求都变化的秒级时间戳直接加入公共 system prompt 后立即上线。**

首先，它可能破坏提示词缓存。模型请求虽然每次都携带 system prompt，供应商仍可能复用此前计算过的相同前缀；“每次都发送”不等于“每次都重新计算”。当时间戳变化时，从该变化位置向后的前缀就不再相同，后面的长对话和工具结果也可能无法复用。受影响的计算量可能远大于新增的一行文字。Cindy 的 [Agent 工程规则第 3.1 节](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/docs/dev-rules/maker-core-and-agent-behavior.md#L713) 明确禁止向稳定前缀加入每轮变化的时间戳；[Claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#structuring-your-prompt) 和 [OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching) 的官方缓存文档也要求保留稳定前缀，将动态内容放到后面。

缓存影响从时间戳发生变化的位置开始。此前满足缓存条件的稳定前缀仍可复用；后续的复用范围由模型、缓存边界、有效期和 SDK 最终请求决定。上线前应对比真实请求与用量，量化这部分影响。

其次，方案没有说明时间属于谁。`2026-08-25 14:32:07` 没有时区，远程执行电脑或服务器的日期未必等于用户所在地日期；“这周”还涉及一周从哪天开始。对于日期类问题，秒级变化没有相应收益。题目中的日期是示例；实际日期应在运行时生成，并在跨日后自动更新。

最后，近期事实需要检索支撑，时钟负责提供正确的时间参照。公共 system prompt 还会影响经过该路径的非时间任务，这是一处覆盖广泛的行为改动。Cindy 的 [system prompt 改动规则](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/docs/dev-rules/maker-core-and-agent-behavior.md#L749) 要求先讨论行为与缓存影响，再经维护者确认和实测；因此应完成行为、缓存和性能评估后再安排上线。

### 2. 如果上线，会发生什么？谁受影响、影响多大、能否发现？

| 影响 | 受影响对象与程度 | 如何发现 |
|---|---|---|
| 日期回答可能改善 | 缺少时间参照的用户可能不再遇到“按去年回答”；但仍可能受时区、旧上下文或模型理解错误影响 | 用固定时钟核对今天、昨天、本周的实际日期范围，并检查用户纠正日期的反馈 |
| 缓存下降、成本和首字延迟上升 | 所有经过被修改请求路径的用户，包括只问代码或写作的人；长对话、长工具上下文及多步 Agent 的累计影响更大 | 对比同模型、相近输入长度下的缓存读取/写入 token、未缓存输入、单任务成本及首字延迟 P50/P95 |
| 跨时区或跨日答错 | 手机远控另一台电脑、旅行或长期打开会话的用户，可能错一天、跨到错误的一周甚至年份 | 对照用户时区测试午夜、跨年、周边界和夏令时；检查上下文中的时间来源与采样时刻 |
| 日期正确但事实仍错 | 询问最新新闻、版本或事件的用户仍可能得到过时信息，甚至因日期看起来正确而更信任回答 | 检查检索的日期范围与引用的事件发生时间，同时核验日期解释和事件事实 |

**成本影响可以通过缓存命中率估算。** 举例：假设一条请求有 100,000 个输入 token，原来 80% 命中缓存；再假设缓存读取单价是普通输入的 10%。原输入成本相当于 28,000 个普通输入 token；若这些命中全部丢失且改按普通输入计费，就变为 100,000，约为原来的 **3.57 倍**。这个假设示例展示输入成本的变化；完整开销还包括缓存写入费、输出费和订阅计费。线上影响按各路由的实际 token 用量和价格统计。

这类回退可能没有报错：功能仍返回正常文本，单测和类型检查也可能全绿。只测一次“今天几号”很容易漏掉。Cindy 已有 [UsageTracker.getCacheStats()](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/packages/maker-core/src/agents/shared/usage-tracker.ts#L440)，提供 turn/session 两个粒度的缓存数据；其口径为 `read / (read + create + uncachedInput)`。比较时结合请求次数，将冷启动和预热后的结果分开统计；供应商未报告的字段标记为缺失。

### 3. 我的方案：自动提供可靠时间，同时保留可复用前缀

**在当前轮上下文中提供日期、时区及必要的时间范围；稳定 system、工具定义和既有历史保持不变。** 时间获取和日期计算由宿主代码完成，用户无需每轮提醒，也不需要安装插件或填写 Key。

1. **确定时间来源。** 优先采用用户明确设置的时区，否则采用发起请求的客户端时区，并将其随远程请求传递；后台任务使用已保存的任务时区。记录采样时刻与来源，发现明显时钟偏差时使用可信校时结果修正。校时异步完成，保持模型请求发送流畅。
2. **在新一轮消息末端附上简短时间上下文。** 默认提供本地日期和 IANA 时区；“这周”的起止日期由日期库按用户区域设置计算，回答时可写出明确日期范围。如果用户指定历史时间或其他时区，以该问题的参照为准。建议传入的数据格式如下，以本次作答日为例，一周从周一开始：

   ```text
   本轮时间参照：2026-10-31
   用户时区：Australia/Sydney（UTC+11:00）
   本周日期：2026-10-26 至 2026-11-01
   ```

3. **保持历史不变，自动更新当前参照。** 每个新用户轮次重新取日期；跨日、切换时区或恢复旧会话时，在新的上下文位置追加最新值，不回写旧消息中的时间。正常工具循环和重试复用该轮快照；耗时任务若需要真正的“现在”，再读取时钟，并在新的消息或工具结果位置追加更新。精确到秒的需求按需获取，不给所有请求持续注入秒级变化。上下文压缩或恢复后，要保证最新时间参照仍在，同时保留历史消息原有的时间含义。
4. **按 SDK 最终请求的位置接入。**当前源码的 [`StartSessionOptions.userPrompt`](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/packages/maker-core/src/agents/base-agent.ts#L1988) 是会话启动时的 system 追加段；[Claude 的拼装代码](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/packages/maker-core/src/agents/claude-code/index.ts#L253) 确实把它放入 system。实现时应逐一检查 Claude Code、Codex、Pi 的实际消息构建入口，将动态数据放入当前轮消息的宿主上下文部分，并核验最终请求及缓存边界。仅仅追加到 system 最后，仍可能让后面的全部历史失去缓存。落地时分别适配这三条消息发送链路。
5. **对新近事实主动检索。** “这周有什么新闻”应按已确定的日期范围查询可用来源，区分发布日期与事件发生日期并引用依据。来源暂不可访问时提示检索失败，并保留已确定的查询时间范围，便于重试。日期计算类问题则可直接使用宿主时间与日期库。

上线前先做两类验证：一类是固定时钟下的今天/昨天/本周、跨日/跨年/闰日/夏令时、远程端时区、恢复与压缩、明确历史日期等用例，并检查普通代码和写作任务是否回退；另一类是在相同模型和代表性长短会话中，对比“现状、同事方案、上述方案”的时间回答正确率、缓存数据、输入成本和首字延迟。连续多轮测试应在可比的缓存有效期内运行，分开统计冷启动和预热后的结果。

通过后按用户或会话小范围灰度，跟踪准确率、用户纠正反馈、缓存和性能；预先约定成本与延迟预算，超出预算就关闭新注入路径并回滚。若最终仍需改 system 段，先走仓库要求的维护者确认流程。验收目标是用户无需提醒日期仍能得到正确的时间解释，并且非时间任务没有不可接受的成本、速度或质量回退。

依据为 Cindy 固定源码 `f283ccebd3b9ef11d89807934b6ccafec6ef23a4` 和 2026-10-31 查阅的官方缓存文档。源码与接口核验已完成；A/B 实验和灰度属于后续实施步骤，用于测量实际成本与延迟。

## A2 配置排查报告审阅

**我会先核对版本发布契约，做一个只改变 `updatedAt` 的对照实验，再决定修复哪一层。按 Cindy 的现有契约，应优先修正发布版本，而不是启动一周的客户端重写。**

题目已明确代码、路径、时间戳和条目数量都属实。这份报告的核心问题在于：它找到了保留旧缓存的执行条件，却直接把这个条件判为设计缺陷，跳过了“这段保护为什么存在、发布方是否遵守版本协议”的判断。

### 1. 采信报告和启动重写之前，我会做什么？

**第一步，查清 `updatedAt` 的协议含义。** 要确认它是普通展示时间，还是决定配置新旧的版本标识。Cindy 的 [目录发布规则](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/docs/dev-rules/model-catalog-maintenance.md#L321) 明确要求：新 revision 递增，同一 revision 的内容保持不变；更新目录时要增加 `updatedAt`。因此，45 条变成 46 条而版本仍为 `2026-08-01T00:00:00Z`，属于同一版本被发布成了两份内容。

**第二步，做最小对照实验。** 保存故障客户端的缓存副本，在隔离环境固定客户端版本、目录来源、账号条件和配置内容：

- 对照 A：缓存为 45 条，远端为 46 条，两边 `updatedAt` 相同，记录最终采用的版本与目标模型是否出现。
- 对照 B：保持这 46 条内容不变，只将远端 `updatedAt` 提升为符合发布规则的新版本，再执行相同刷新流程。

预期 A 保留旧快照，B 采用新快照。B 通过就能说明现有更新链路可以完成这次更新，修复点应先落在发布版本；若 B 未通过，则从下载、解析、版本选择、落盘、活动目录到界面逐层定位，按失败环节修复。先保留现场再做实验，避免清缓存后丢失关键证据。

**第三步，把证据串成同一次刷新记录。** 记录实际请求的环境、URL 与能力参数，响应的 revision、内容摘要、目标模型 ID、缓存 revision，以及最终生效的来源和 revision。对照发布制品、实际接口响应、客户端活动目录和选择器，确认新模型走到了哪一步。`HTTP 200` 或“从远端加载成功”的日志只说明请求链路成功；最终采用哪份快照，应查看版本选择结果。当前 [加载实现](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/packages/model-providers/src/source.ts#L675) 会在下载后与缓存比较，再返回最终目录。

**第四步，验证保护条件和影响范围。** 在相同 schema 和相同目录来源下，至少覆盖下表；另按客户端版本、环境、账号和缓存状态统计受影响用户。

| 场景 | 应有结果 |
|---|---|
| 同版本、同内容 | 视为同一快照，保持内容一致 |
| 同版本、不同内容 | 保留已验证的旧快照，报告版本冲突 |
| 远端版本更高、内容合法 | 整体采用新快照；检查新增模型及其价格、路由 |
| 新配置已经生效，随后旧响应到达 | 保留较新快照，防止回退 |
| 远端超时、结构非法或内容不完整 | 使用最后一份有效配置，保持基本可用 |
| 无旧缓存且内置版本更低 | 合法远端配置可以被采用，与已有同版本旧缓存的客户端分开统计 |

若活动目录已经包含目标模型而界面没有显示，再检查该账号的模型成员资格、引擎支持和用户显示开关。验收应落到具体模型 ID、价格与可用路由，数量 45→46 只是辅助指标。

### 2. 这份报告的问题在哪里？

**把执行机制当成了根因和责任归属。** `<=` 解释了客户端为何保留缓存；发布协议解释了为什么它这样做。该条件用于阻止相同或更旧版本覆盖已采用的配置。按现有契约，本次首先暴露的是发布时内容变了、版本没有递增，以及发布流程缺少相应检查。[源码注释](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/packages/model-providers/src/source.ts#L562) 也明确要求同版本保持内容一致，纠错通过更高版本向前发布。

**把一个缓存条件扩大成“所有用户”。** 受影响的是拿到这份配置、已有同版本旧缓存、并经过该判断路径的客户端。没有旧缓存、使用其他目录来源或采用了更高版本的客户端，应分别检查。这些分组决定问题规模和修复后的验证范围。

**建议删除了原有保护，却没有分析后果。** “始终采用服务端配置”会让延迟到达的旧响应、旧节点或旧缓存内容覆盖已生效的新配置，造成模型、价格或路由回退。逐字段深比较可以发现内容不同，却不能单独判断哪份更新，也不能解决发布顺序问题。简单把 `<=` 改成 `<` 同样会放行同版本不同内容，使最终结果取决于哪份响应后到。深比较适合用于发现版本冲突，版本选择仍应遵守发布协议。

**把“静默”和“一周重写”写成了结论，却缺少对应分析。** 静默问题应检查日志、监控和用户提示各层：当前源码对同版本异内容已有 warning，运维是否收集、能否关联到有效版本，则是可观测性要解决的事。重写工期应建立在复现、影响面和方案比较之上；一次发布版本修正、发布校验和完整加载器重写，是成本与风险明显不同的方案。

### 3. 我会怎样处理和验收？

**先恢复正确发布。** 在发布源生成包含新增模型的完整目录，提高 `updatedAt`，校验结构后按正常流程发布。新 revision 应高于当前已发布、供该客户端比较的相关版本。随后回读实际接口，检查 revision、目标模型、价格及 ETag，再让保留原缓存的受影响客户端按正常流程刷新。这样直接验证用户是否已看到新模型，也保留了原有版本保护。仓库的 [维护步骤](https://github.com/makecindy/cindy/blob/f283ccebd3b9ef11d89807934b6ccafec6ef23a4/docs/dev-rules/model-catalog-maintenance.md#L108) 要求内容变更递增版本，回撤也使用新的完整 revision。

**再补发布校验。** 由发布工具统一生成递增 revision；CI 对照已发布制品，拦截“同版本、不同内容”和版本倒退。发布后自动回读实际接口，核对版本、内容摘要与关键模型，发现遗漏时及时阻止或纠正发布。若需要回滚内容，将恢复后的内容发布为更高 revision，继续保持版本顺序。

**最后补更新结果的可观测性。** 刷新记录应包含远端版本、缓存版本、最终版本和采用原因，例如采用新版本、保持现有版本、同版本冲突、解析失败。聚合同版本冲突告警；手动刷新遇到冲突时提示“目录版本冲突，已保留上次可用配置”。这些记录既能帮助运营定位发布问题，也能衡量实际影响范围。

验收覆盖：原有 45 条缓存的客户端正常更新；无旧缓存的客户端获得正确目录；旧响应、离线和坏配置继续受到保护；新模型及价格正确显示，原模型的删除/停用语义和用户设置保持正确。若提高版本后仍有某一步失败，就针对该环节提交修复，用失败用例验证，而不是直接扩大成整套加载器重写。
