# 收工

按下面四步顺序执行，每步记录证据后再进入下一步。测试失败也要继续审阅与残留检查，最后统一报告。使用当前项目已有的文件、Git 和命令执行工具，无需专用插件。

## 开始前：确定项目和本次范围

- 使用用户指定的项目或当前任务工作目录，读取适用的 `AGENTS.md`、贡献指南和测试配置。
- 先看 `git status --short`，记录分支及 `git rev-parse HEAD`，保留开始时已有的改动。
- 优先采用用户指定的提交范围；否则采用本任务开始时已记录的提交作为 `BASE`，审阅 `BASE..HEAD` 加工作区全部相关改动。用户给的是目标分支时，先取它与 `HEAD` 的 merge-base。把 `BASE` 解析成真实提交，后续使用该固定值。
- 没有可用基线时，先检查暂存、未暂存和未跟踪文件，并在摘要写清范围。已提交内容的归属只有靠用户补充才能确定时，询问起点，同时继续检查已确定的内容；不要把 `HEAD~1` 当作本次任务的默认起点。
- 同一工作区混有其它人的改动时，一并列入清单但标明归属；只处理本任务范围。非 Git 项目使用本任务已记录的文件清单及原始副本比较，并说明范围。

## 1. 跑一遍测试

1. 按以下优先级确定测试命令：用户明确要求 → 项目规则与贡献指南 → CI 定义及实际测试脚本。先读脚本内容，再执行；不要根据语言猜命令，也不要用空的 `test` 占位脚本充当测试。
2. 执行项目要求的测试集。项目没有明确规定时，选择覆盖本次变更模块的现有测试，并说明范围；跨模块公共代码应覆盖受影响调用方。使用已有的单次运行方式，避免留下 watch 进程。
3. 记录工作目录、完整命令、退出码和结果；工具提供用例数时一并记录。区分“通过”“失败”“未运行”。只有构建或 lint 时按实际名称报告，不能写成测试通过。
4. 测试失败时保留失败用例与关键错误，继续第 2 步。没有测试、缺依赖或缺外部服务时记录具体缺项；不编造通过记录，不为凑绿灯而改测试或跳过断言。

## 2. 从头到尾审阅本次改动

1. 先建立文件清单：有 `BASE` 时运行 `git diff --name-status BASE HEAD`；再运行 `git diff --name-status`、`git diff --cached --name-status`、`git ls-files --others --exclude-standard`。命令中的 `BASE` 替换为开始前解析出的提交。
2. 按文件路径顺序逐个审阅，覆盖已提交、暂存、未暂存、新增、删除与重命名。分别读取 `git diff BASE HEAD -- <path>`、`git diff --cached -- <path>`、`git diff -- <path>`；未跟踪源码直接打开完整文件。某一层为空不代表其它层没有改动。
3. 阅读每个 diff hunk，并查看理解其行为所需的上下文、调用处与测试。大 diff 分段读到末尾，不以 `--stat`、搜索命中或被截断的输出代替完整审阅。
4. 对照本次需求检查：行为是否正确、失败分支是否处理、接口与配置是否一致、测试是否覆盖变化。发现问题记录 `路径:行号`、触发条件和影响。
5. 二进制或生成文件检查可用预览、生成来源和对应源码；无法查看的文件明确列出，不将其标成已完整审阅。不要为了审阅自动重生成文件。

## 3. 检查临时调试残留

1. 对第 2 步清单中的文本文件搜索调试线索，例如：

   ```text
   rg -n -i -e 'console\.(log|debug)|debugger|\bbreakpoint\s*\(' -e 'TODO|FIXME|HACK|DEBUG' -e 'localhost|127\.0\.0\.1|mock|dummy|test[-_]?token' -- <改动的文本文件路径…>
   ```

   这是候选线索；按项目语言补充临时 `print`、调试开关等。另人工查看新增常量、固定用户 ID、固定返回值、绕过正常分支和临时测试地址，字符串搜索覆盖不到所有写死的测试值。
2. 逐项结合 diff 和用途判断。正式 CLI 输出、项目日志、测试夹具与文档示例可以保留，并简记保留理由；临时打印、业务路径中的假数据和调试绕过列为残留。不要按关键词批量删除。
3. 本次任务中明确的临时残留可直接清理；需要业务决定的常量或非本任务改动保留，并记录待处理位置。收尾不顺带重构或修改其它人的工作。
4. 如有清理或修复，重跑受影响测试，再审阅新增 diff、复查残留。将这些补充动作记录在原步骤下；最终测试结果必须对应清理后的文件。若检查期间出现新改动，也按此规则补查后再给结论。

## 4. 给出简短收工摘要

按下面格式回答，通常控制在一屏；有阻塞项时列出最关键的证据。

```text
收工状态：已完成 / 待处理
范围：项目、基线与纳入的文件；范围缺口写在这里。
改动：本次实现了什么，影响哪个行为（1–3 条）。
测试：工作目录、命令、退出码、通过/失败/未运行；复测结果。
审阅：已读范围、发现的问题（路径:行号）或“未发现需处理项”。
调试残留：清理内容、保留项及理由；没有则写“未发现临时残留”。
待处理：失败测试、范围缺口、未审完文件或尚需决定的事项；没有写“无”。
```

项目要求的检查通过、审阅与残留检查完成、无待处理项时，状态为“已完成”。无自动化测试时列明该事实及已做的替代检查，状态为“待处理”，由用户决定是否接受；不把“流程执行完”写成“质量检查通过”。

“收工”本身不包含 commit、push、发布、合并或清理整个工作目录；只有当前任务另有明确要求时才执行这些动作。
